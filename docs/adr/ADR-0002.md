## 1. Contexto

Con [ADR-0001](ADR-0001.md) se extraerán **Order**, **Kitchen** y **Delivery** en fases. Los UCs del FSD implican **múltiples handoffs** con cambio de estado: confirmación de pedido (UC-01), ticket en cocina (UC-02), asignación y tracking (UC-03, UC-05, UC-06), pago y retry (UC-04). Durante la migración, el monolito y los servicios nuevos deben interoperar sin comprometer **disponibilidad del pedido** (NFR-02), **tracking** (NFR-03), **resiliencia de pago** (NFR-04) ni **trazabilidad end-to-end** (NFR-08).

**Restricciones:**

| ID | Restricción | Origen |
| --- | --- | --- |
| R1 | Toma de pedidos ≥ 99,9 % mensual | NFR-02 · [Brief §A.4](../contexto.md#a4-restricciones-técnicas-y-nfrs-base) |
| R2 | Tracking ≥ 99,5 % (puede degradar vs. pedido) | NFR-03 · [Brief §A.4](../contexto.md#a4-restricciones-técnicas-y-nfrs-base) |
| R3 | Pedidos posibles con pasarela caída + cola retry | NFR-04 · UC-04 · [Brief §A.4](../contexto.md#a4-restricciones-técnicas-y-nfrs-base) |
| R4 | Correlation ID en acciones del consumidor | NFR-08 · [Brief §A.4](../contexto.md#a4-restricciones-técnicas-y-nfrs-base) |
| R5 | Pico 5× almuerzo/cena | NFR-05 · [Brief §A.4](../contexto.md#a4-restricciones-técnicas-y-nfrs-base) |
| R6 | Coexistencia monolito/servicios en Strangler | [ADR-0001](ADR-0001.md) |

## 2. Opciones consideradas

### Opción A — REST síncrono exclusivo (HTTP/JSON)

**Descripción:** Todas las integraciones entre servicios y con el monolito vía APIs REST; sin broker de mensajes.

| Pros | Contras | Impacto NFR |
| --- | --- | --- |
| Simple de depurar; familiar para el equipo Java/Spring | Acoplamiento temporal fuerte; cascadas de fallos | **NFR-02** ↓ si un servicio lento bloquea la cadena |
| Baja latencia en lecturas | Picos 5× amplifican contención | **NFR-05** ↓ |
| — | Difícil modelar retry de pago sin polling | **NFR-04** débil |

**Origen:** Patrón API Gateway / servicios REST (Richardson); válido para consultas, insuficiente solo para transiciones de estado.

---

### Opción B — Mensajería asíncrona exclusiva (event bus / Kafka)

**Descripción:** Solo eventos de dominio entre servicios; APIs REST solo en el borde (apps móvil/web).

| Pros | Contras | Impacto NFR |
| --- | --- | --- |
| Desacoplamiento y absorción de picos | Consistencia eventual visible al usuario | **NFR-01** puede degradar en lecturas “inmediatas” |
| Natural para notificaciones y tracking | Mayor complejidad operativa (broker) | **NFR-03** mejorable si eventos son fuente de verdad |
| Alineado con NFR-04 (colas) | Curva de aprendizaje y ordering/idempotencia | **NFR-08** requiere propagación de correlation ID en headers de mensaje |

**Origen:** Richardson — messaging, event-driven architecture; [Brief §A.4](../contexto.md#a4-restricciones-técnicas-y-nfrs-base) tolerancia a fallos externos.

---

### Opción C — Híbrido: REST en consulta/comandos síncronos críticos + eventos en transiciones de estado

**Descripción:** **REST/gRPC** para operaciones que requieren respuesta inmediata al usuario (confirmar pedido, aceptar ticket con ETA). **Eventos de dominio** (`OrderCreated`, `TicketAccepted`, `DeliveryAssigned`, `PaymentPending`) para notificar a Kitchen, Delivery, Billing y Notifications. Broker (p. ej. Kafka) como backbone en fases 2–3.

| Pros | Contras | Impacto NFR |
| --- | --- | --- |
| Balance latencia UX y desacoplamiento | Dos modelos mentales (sync + async) | **NFR-01** en REST de confirmación; **NFR-02** protegido |
| Cola de pago y reasignación courier vía eventos | Riesgo de duplicados → idempotencia obligatoria | **NFR-04**, **NFR-06** (UC-06) mejor soportados |
| Monolito puede publicar/consumir eventos vía ACL | Infra adicional (broker, schemas) | **NFR-08** con correlation ID en HTTP y en mensajes |

**Origen:** [FSD UC-01..06](../fsd/FSD_v1.md); Richardson — combinación API + messaging; coherente con C4 que debe mostrar broker si hay async.

---

### Opción D — Integración solo vía base de datos compartida (anti-patrón)

**Descripción:** Servicios leen/escriben tablas del monolito sin APIs ni eventos.

| Pros | Contras | Impacto NFR |
| --- | --- | --- |
| Rápido en fase 0 | Acoplamiento de esquema; impide DB-per-service | **NFR-06** y **NFR-07** violados a medio plazo |
| — | No Strangler limpio | Penaliza migración [Brief §A.6](../contexto.md#a6-restricciones-del-laboratorio) |

---

## 3. Decisión

**Se adopta la Opción C — IPC híbrido (REST + eventos de dominio).**

**Reglas de uso:**

| Tipo de interacción | Mecanismo | Ejemplos (FSD) |
| --- | --- | --- |
| Comando con respuesta inmediata al actor | REST (Spring Web) | UC-01 confirmar pedido; UC-02 aceptar ticket; UC-03 aceptar oferta |
| Transición de estado / notificación a otros límites | Evento asíncrono | Pedido creado → Kitchen; listo para retiro → Delivery; pago pendiente → Billing |
| Integración monolito (fase Strangler) | REST + consumer/producer en ACL | Publicar `OrderCreated` desde legacy wrapper |
| Observabilidad | Correlation ID en header HTTP y metadata del evento | NFR-08 · todos los UC |

**Stack acotado:** Java/Spring Boot; Spring Kafka o equivalente en fases 2–3 [Brief §A.4 — Tecnología](../contexto.md#a4-restricciones-técnicas-y-nfrs-base).

**Justificación:** Satisface latencia en checkout (NFR-01), desacopla Kitchen/Delivery en picos (NFR-05), habilita retry de pago (NFR-04) y es coherente con la migración por fases de ADR-0001.

---

## 4. Consecuencias

### Positivas

- Desacoplamiento progresivo sin sacrificar UX en confirmación de pedido.
- El diagrama C4 N2 puede incluir **broker** y relaciones async de forma honesta.
- Reasignación de courier (UC-06) y notificaciones (UC-05) escalan con consumidores independientes.

### Negativas

- **Complejidad operativa:** broker, topics, esquemas de eventos, monitoreo de lag.
- **Consistencia eventual** en vistas secundarias (tracking, dashboard restaurante) — mitigado en ADR-0003.
- Riesgo de **mensajes duplicados** → exige consumidores idempotentes y diseño de eventos.

### Follow-ups

- Definir catálogo mínimo de eventos (`OrderCreated`, `TicketAccepted`, `ReadyForPickup`, `DeliveryAssigned`, `PaymentFailed`, `PaymentCompleted`).
- **ADR-0003:** Saga/outbox para consistencia del pedido.
- **POC:** throughput de publicación en ventana 12:00–14:00 (NFR-05).
